# DECISION / PLAN — `theme.nix` per UI module (2026-11-13)

Status: **Phases 0-3 implemented (2026-11-13); Phases 4-5 planned.** This
document is the implementation brief; see §10 for what actually landed.

## 1. Goal

Give every module that renders a GUI, TUI or Web UI **one `theme.nix` side-car**
that (a) owns that app's `theme` options and (b) applies the repo palette to that
app's real theming surface. Result: theming is *applied* by the module that owns
the surface, while the *contract* and the colour maths stay in one place.

Non-goals:

- A single central `themes.nix` that reaches into every module. It would need to
  know 130+ option namespaces, would break whenever a module is not imported on a
  host, and duplicates what the module system already does. Ownership stays with
  the module; only the *shape* is centralised.
- Inventing theming for apps that have no declarative surface (see §4.3).
- Covering web UIs whose only injection point is HTTP body rewriting (see §4.1 Phase 4 and §4.3).

## 2. Current state (evidence)

The palette layer is already unified and is **not** being redesigned:

| Piece | File |
|---|---|
| scheme → roles / base16 / terminal | `lib/theming.nix` |
| pure colour maths (contrast, mix, alpha) | `lib/color.nix` |
| NixOS read API `my.theming.colors` | `modules/nixos/theming/config.nix:17` |
| Home Manager read API `my.theming.colors` | `modules/home/theming/config.nix:29` |
| flake API `flake.lib.theming` / `lib.color` | `flake.nix:255` |
| stylix bridge | `modules/nixos/stylix/config.nix:18` |

What is *not* unified is application, and three implementations coexist:

1. **Palette-driven, ad hoc.** `modules/home/zed-editor/config.nix:21-162`
   generates a full Zed theme inline; `modules/home/core/git.nix:8` and
   `modules/nixos/gnome/home.nix:10,40` read the palette directly;
   `modules/home/helix-ide/config.nix:13` uses `my.theming.schemeUnderscored`;
   `modules/nixos/homeManager/mcp-wrappers.nix:108-160` generates the opencode
   theme **from a NixOS home-manager side-car**, not from
   `modules/home/opencode`.
2. **Delegated to stylix.** `modules/nixos/stylix/config.nix:19-64` enables
   `autoEnable`; `modules/home/ghostty/options.nix:48-52` leaves
   `theme = null` and relies on stylix; `modules/home/ghostty/options.nix:95-99`
   only offers a `customThemes` escape hatch. Only desktop and laptop enable
   stylix (`configurations/nixos/desktop/default.nix:97`,
   `configurations/nixos/laptop/default.nix:44`); server/wsl hosts have no app
   theming at all.
3. **Hardcoded Catppuccin hexes**, which silently stop matching after a scheme
   switch:
   - `modules/nixos/hyprland/bar/config.nix:245-350` (~37 literals)
   - `modules/nixos/hyprland/notifications/config.nix:7-19` (mako)
   - `modules/nixos/hyprland/lockscreen/config.nix:8-14,22-36` (swaylock + hyprlock)
   - `modules/nixos/proxy/dashboard.nix:19-58` (27 literals, web UI)
   - `modules/nixos/gnome/home.nix:40-41` (dconf accent fallbacks)
   - `modules/home/vscode/options.nix:25,84` (Dracula theme)
   - `modules/nixos/hyprland/bar/config.nix:292-321` (Spotify brand green —
     brand colour, must be preserved, see §7)

There is no per-app way to say "theme this app, but override its accent" and no
machine-readable list of which apps are themed.

## 3. Target architecture

```
lib/color.nix            pure colour maths                      (unchanged)
lib/theming.nix          scheme → roles / base16 / terminal      (+ recolor, §3.3)
lib/theme.nix   NEW      adapter toolkit: mkAppTheme, cssVars, ansi16, xterm
flake.nix                also expose flake.lib.theme             (+ 1 line)
modules/{nixos,home}/theming/   contract docs + palette mirrors  (docs only)

modules/<kind>/<app>/
├── options.nix          everything EXCEPT thematic options
├── config.nix           everything EXCEPT the theme application
├── theme.nix   NEW      app's `theme` option + application to its surface
├── tests.nix            + palette assertions for this app
└── default.nix          imports = [ ./options.nix ./config.nix ./theme.nix ./tests.nix ]
```

Three rules make this "unified but specialised":

1. Every `theme.nix` declares exactly one option at `my.<same-namespace>.theme`
   using the shared `themeLib.mkAppTheme { base = config.my.theming.colors; }`.
2. Every `theme.nix` applies that palette **only** to its own app's option tree,
   gated on `cfg.enable && cfg.theme.enable`, and never enables the app itself.
3. Every `theme.nix` is the single owner of its app's colours; `options.nix` and
   `config.nix` lose their colour code in the same commit.

### 3.1 The `theme.nix` contract

Template (Home Manager; the NixOS form is identical except the option path):

```nix
# modules/home/ghostty/theme.nix — ghostty's slice of the shared palette.
{ config, lib, ... }:

let
  cfg = config.my.programs.ghostty;
  themeLib = import ../../../lib/theme.nix { inherit lib; };
  theme = cfg.theme;
  p = theme.palette;
in
{
  # Declared here, not in options.nix: everything about this app's theming lives
  # in one file (see docs/decisions/2026-11-13-theme-nix.md).
  options.my.programs.ghostty.theme = themeLib.mkAppTheme {
    base = config.my.theming.colors;
  };

  config = lib.mkIf (cfg.enable && theme.enable) {
    programs.ghostty = {
      settings.theme = lib.mkDefault p.slug;
      themes.${p.slug} = {
        background = p.background;
        foreground = p.foreground;
        cursor-color = p.cursor;
        selection-background = p.selection;
        selection-foreground = p.selectionText;
        palette = themeLib.ansi16 p;      # [ "0=#…" … "15=#…" ]
      };
    };
  };
}
```

Rules and gotchas:

- `default.nix` imports `./theme.nix` **unconditionally** so the options always
  exist on hosts where the module is imported; only `config` is gated.
- The gate is `cfg.enable && cfg.theme.enable`. A theme must never turn a program
  on (`programs.X.enable` stays owned by `config.nix`).
- `theme.enable` defaults to `true` (via `mkAppTheme`) — enabling the app should
  theme it; `false` is the escape hatch.
- No `mkForce`. Hosts and users override through the normal option priority.
- No hex literals in `theme.nix` except a documented `brand` allow-list (§7).
- Home-module `theme.nix` must evaluate with a defaulted `flake` (standalone
  Home Manager); `config.my.theming.colors` already does
  (`modules/home/theming/config.nix:11-26`), so no new fallback is needed.
- NixOS `theme.nix` runs on hosts without stylix (server/wsl); it must not read
  `config.stylix.*`.

### 3.2 The shared option shape

`themeLib.mkAppTheme` returns an option declaration (a `lib.mkOption` whose type
is a `types.submodule`), so every themed app exposes the same four things, plus
whatever the app adds:

| Option | Type | Default | Meaning |
|---|---|---|---|
| `theme.enable` | bool | `true` | apply this app's theme when the app is enabled |
| `theme.overrides` | attrsOf hex | `{}` | per-app base16/role overrides, re-derived like the global ones |
| `theme.palette` | attrs, read-only | derived | global palette + `overrides`, re-derived roles; introspectable via `nix eval` |
| `theme.<app-specific>` | — | — | declared via `extraOptions` (e.g. `opacity`, `wallpaper`, `extraCss`) |

This is the unification the request asks for: same names, same semantics, same
read-only palette for introspection and tests. The app-specific knobs keep it
specialised without a second bespoke option shape per module.

### 3.3 `lib/theme.nix` (new) and the one change to `lib/theming.nix`

`lib/theming.nix` currently builds everything inside `mkColors`
(`lib/theming.nix:198-250`); there is no way to re-derive roles from an already
resolved palette. Extract that assembly into an internal `assemble` and expose:

```nix
theming.recolor = { palette, overrides ? { } }: …   # same output shape as mkColors
```

`recolor` takes `my.theming.colors` (it carries top-level `base00`-`base0F` with
`#`, hashless `base16`, and identity), applies pass-1 base overrides / pass-2
role overrides exactly like `mkColors`, and returns the identical shape. This is
what makes per-app `overrides` correct: overriding `background` also moves
`onBackground`, `selection`, etc. — no stale dependent role.

`lib/theme.nix` (pure, `{ lib }:` only, no flake/module deps):

```nix
{ lib }:
let
  theming = import ./theming.nix { inherit lib; };
  inherit (theming) color;
in
{
  inherit color;                      # contrast / mix / alpha / valid
  recolor = theming.recolor;          # per-app palette derivation

  mkAppTheme = { base, extraOptions ? { } }: …;  # option declaration; §3.2
  cssVars    = { palette, prefix ? "theme", extra ? { } }: "…";  # :root { --theme-…: …; }
  ansi16     = palette: [ "0=#…" … "15=#…" ];    # ghostty `palette =`
  ansi16Values = palette: [ … 16 hex … ];        # bare list (qutebrowser, xterm)
  xterm      = palette: { background; foreground; cursor; … };  # ttyd clientOptions
}
```

Deliberately **not** in the toolkit: TOML/KDL/YAML serialisers. Each `theme.nix`
renders its own format with `lib.concatStringsSep` / `pkgs.formats.*`, because
that mapping is the app-specific part; putting one serialiser per format in the
lib would recreate the duplication we are removing.

`flake.nix:217` already imports `lib/theming.nix` for `flake.lib`; add
`theme = import ./lib/theme.nix { lib = inputs.nixpkgs.lib; };` to the same block
so scripts and audits can use the toolkit without a module system.

### 3.4 `meta.nix` extension

Add one optional block (backs §5's coverage test and the agent inventory):

```nix
theme = {
  kind = "gui";          # gui | tui | web
  mechanism = "generated";  # native | generated | css-inject | stylix | none
  file = "theme.nix";    # omitted when mechanism = "none"
};
```

`mechanism = "none"` records a UI module that has no declarative surface, with a
`reason`, so the next agent does not re-investigate it.

### 3.5 Convention docs

`modules/AGENT.md` §1.1 (directory schema) and §2 (file responsibilities) gain a
`theme.nix` row, plus a new §2.2 stating: theming is owned by `theme.nix`;
`options.nix` must not declare `theme`; `config.nix` must not contain colour
code; `theme.nix` is required for modules whose `meta.theme.mechanism != "none"`.
`modules/{nixos,home}/theming/README.md` gain the contract + the themed-app list.

## 5. Rollout plan

### Phase 0 — scaffolding, no visual change

1. `lib/theme.nix` (§3.3) + `flake.lib.theme` wiring (`flake.nix`, one line).
2. `lib/theming.nix`: extract `assemble`, add `recolor`; keep `mkColors` output
   byte-identical (guard with the existing tests in `tests/theming_test.nix`).
3. `tests/theming_test.nix`: `recolor` cases — no overrides is idempotent; a
   `background` override re-derives `onBackground`/`selection`; a `base00`
   override moves every dependent role; an unknown role still wins outright.
4. `modules/AGENT.md` §1.1/§2 + new §2.2; `meta.nix` `theme` block (§3.4).
5. Two theming READMEs get the contract and the Phase-1/2 list.
6. New nixtest `tests/theme-coverage_test.nix`: for every module directory with
   `meta.theme.file == "theme.nix"`, the file exists; no `theme.nix` exists
   without the meta block. (Pure eval of `builtins.readDir` fixtures.)
7. Exit criterion: `nix flake check --no-build` green, no host diff in
   `nixos-rebuild dry-activate`.

### Phase 1 — Home Manager apps (start with zed)

Order: `zed-editor` → `ghostty` → `helix-ide` → `qutebrowser` → `vscode` →
`opencode` → `firefox` → `thunderbird` → `spotify`.

- `zed-editor` first: it is the only complete implementation, so it proves the
  template and gives a golden diff (`nix eval --json` of the generated theme
  before/after must be equal apart from module placement).
- `opencode` moves the generator out of
  `modules/nixos/homeManager/mcp-wrappers.nix:108-160` into
  `modules/home/opencode/theme.nix`; `homeManager/config.nix:333` then consumes
  `config.my.programs.opencode.theme.themes` instead of a local binding, and the
  `flake.config.my.theming` read disappears from the NixOS side.
- `firefox`/`thunderbird` add `stylix.targets.<app>.enable = mkDefault false` to
  `modules/nixos/stylix/config.nix` **in the same commit** as the new
  `theme.nix` (precedent: the zed target opt-out at
  `modules/nixos/stylix/config.nix:88-90`), so two owners never fight.
- `spotify` keeps `#1db954` as a declared brand colour; the waybar
  `custom-spotify-*` hexes move to `hyprland/bar/theme.nix` in Phase 2.

Per-module done criteria:

- `theme.nix` exists and is imported by `default.nix` (or by `home.nix` for
  HM-side modules such as `gnome/home.nix`).
- `options.nix` no longer declares `theme`; `config.nix` no longer computes
  colours.
- `meta.nix` has the `theme` block; `tests.nix` asserts the app's `theme.palette`
  is complete and the applied values are non-empty.
- Host eval of both a stylix host (desktop) and a non-stylix host (server/wsl)
  succeeds.

### Phase 2 — NixOS desktop

`hyprland/bar` → `hyprland/notifications` → `hyprland/lockscreen` →
`hyprland/appearance` → `hyprland/utilities` → `gnome` →
`hyprland/display-manager`.

- `bar`: build `style.css` from `themeLib.cssVars` + role-based rules; the
  custom-module `format` examples in `bar/options.nix:26,167` must reference
  roles, not hexes.
- `notifications`/`lockscreen`: attribute sets, not string interpolations, before
  rendering (`background-color=${p.surface}` etc.).
- `utilities`/`gnome`: when `config.stylix.enable` is true the stylix target owns
  GTK/Qt; `theme.nix` must then only set `theme.palette` and skip writing GTK
  names (mirror the existing `!(config.stylix.enable or false)` guards at
  `modules/nixos/gnome/home.nix:61,81`).
- `appearance`: shadow colour default becomes `p.background` + alpha, but keep the
  option so hosts can still hardcode a value (no `mkForce`).
- Exit criterion: desktop `nixos-rebuild dry-activate` shows only the file
  contents changing (no option removals), and a `theming.scheme` flip to e.g.
  `catppuccin-latte` visibly changes every themed surface.

### Phase 3 — Web UIs

- `proxy/dashboard.nix` is a plain function file (not a module); thread the
  palette in from `config.nix` (`dashboard.nix` already receives `cfg`), or add
  `theme` to its arguments. CSS values come from `p.*`, not literals.
- `ttyd`: `services.ttyd.clientOptions.theme = builtins.toJSON (themeLib.xterm p)`
  behind `cfg.theme.enable`.
- `monitoring`: set Grafana's default theme from polarity only; do not claim
  custom CSS.
- Exit criterion: dashboard HTML renders with the active palette; ttyd xterm
  colours match the terminal in a browser.

### Phase 4 — deferred items

Only if requested: obsidian snippet (opt-in, never on by default), rstudio prefs,
JupyterLab theme extension, obs-studio `.qss`. Each needs its own small decision
record because they touch user data or upstream packages.

### Phase 5 — enforcement (ratchet)

Add `checks.theme-literals` (like `checks.ventoy-deploy-tests` in
`modules/flake-parts/ventoy/deploy.nix:195`): grep `modules/**/*.nix` for
`#[0-9a-fA-F]{6}` outside `lib/schemes/`, `modules/*/theming/`, `*/theme.nix` and
an explicit brand allow-list (`#1db954`). Start with the current offenders in a
baseline list and shrink the list to empty as Phases 1-3 land; then remove the
baseline. This is the guard that stops hardcoded Catppuccin from creeping back.

## 6. Verification

Per phase, in this order:

```bash
git add <new files>                    # only new paths; never `git add -A` (AGENTS.md §8)
nix fmt
nix flake check --no-build
nix eval --json .#nixosConfigurations.desktop.config.my.programs.<app>.theme
nix eval --json .#nixosConfigurations.server.config.home-manager.users.seanc.my.programs.<app>.theme
nix run .#nixtests-run                 # theming + new coverage suite
nixos-rebuild dry-activate --flake .#desktop   # one host at a time; check free -h first
```

For generated themes (zed, vscode, ghostty, helix, opencode) keep a golden-check
in the module's `tests.nix`: assert required keys exist and every value is a
valid `#[0-9a-f]{6}` (`my.theming.lib.color.valid`), which catches a role rename
that would otherwise produce a silently broken theme file.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Option shape change is breaking | No host or profile sets a module's `.theme` today; the only existing setter is `modules/home/core/git.nix:83` (lazygit, out of scope). Reshape freely, but keep `theme = string` compatibility where the app genuinely takes a theme *name* (`zed.theme` uses `either`) |
| `theme.nix` accidentally enables the app | Gate on `cfg.enable`, never set `programs.X.enable`; Phase-0 template review + a coverage test asserting the app's own enable option is untouched |
| stylix and `theme.nix` both write the same app | One owner per app, recorded in `meta.theme.mechanism`; disable the stylix target in the same commit (zed precedent) |
| Read-only `palette` + submodule defaults recurse | `default` references only the sibling `overrides` option, never `palette` itself; Phase-0 unit test evaluates `mkAppTheme` standalone |
| Web UIs only support body rewriting | Not attempted (needs a Caddy `replace`/`sub_filter` plugin the default build lacks); deferred with a recorded reason |
| Brand colours break the literal guard | Explicit `brand` allow-list in `lib/theme.nix`/docs; guard baseline starts with the known sites |
| Eval cost / build memory | Each `theme.nix` imports one pure lib (`lib/theme.nix`); no new derivations except generated theme files already produced today; hosts built one at a time |
| Stale hardcoded colours return | Phase-5 grep check + `meta.theme` coverage test |

## 9. Open decisions

1. **Namespace** — recommended: keep the app's own path
   (`my.programs.<app>.theme`, `my.services.<app>.theme`). Alternative: a central
   `my.theming.apps.<app>` registry (easier to audit in one place, but the option
   only exists on hosts that import that module, and it moves theming away from
   the app). Recommendation stands: colocated + `meta.theme` for the audit.
2. **Deferred web UIs** — accept "no theme.nix" for Jellyfin/`*arr`/Open WebUI
   etc. (recorded as `mechanism = "none"`), or take on a Caddy response-rewriting
   plugin later as a separate decision.
3. **`utilities`/`gnome` GTK ownership** — default to stylix when it is enabled,
   `theme.nix` otherwise (as today). Confirm this precedence is desired.

Deviations from the plan, and why:

- **opencode**: the V2 CLI reads `cli.json`, and the repo's V1 `defs` theme is not
  a V2 theme. Moving the generator to the module is a pure relocation; stylix's
  opencode target remains the V2 owner (`cli.theme.name = "stylix"`).
- **firefox / thunderbird**: `defaultEnable = false`. `userChrome.css` is
  unsupported by Mozilla and a broken rule is worse than no theme; enabling is a
  per-host decision, documented in each module.
- **helix zellij**: not given a generated theme — zellij's default theme already
  follows the terminal ANSI palette that ghostty's generated theme sets.
- **vscode**: our colour customizations layer on top of stylix's base theme
  instead of disabling stylix's vscode target, because that target also supplies
  the font settings (editor/terminal/markdown sizes). `workbench.colorTheme` is
  `mkDefault`, so stylix wins where present and ours applies on non-stylix hosts.
- **stylix interplay** lives in `modules/nixos/stylix/config.nix` (one
  `home-manager.sharedModules` entry), not in the app modules: a `mkIf false`
  definition of a missing option path still fails option lookup, and reading
  `config` in `optionalAttrs` at module top level recurses (both observed here).

Notes:

- **The dashboard had 64 colour literals in 23 distinct values** (the inventory
  said 27 in the CSS block; the inline JS/HTML carried the rest). All of them now
  come from role names in `theme.nix`; `dashboard.nix` contains none.
- **Three-tier text hierarchy**: `foregroundSubtle` (base03) is a *surface*
  colour in every base16 scheme, so using it for text made card descriptions
  nearly unreadable (`#45475a` on `#181825`). The map derives `muted`/`faint` by
  mixing toward foreground/background instead.
- **`theme.enable = false` keeps the old look**: `theme.nix` carries the
  pre-theming literal set as a documented fallback, so opting out is a no-op
  rather than an unstyled page.
- **Grafana** stops at dark/light: OSS has no custom-CSS hook, so claiming more
  would be false. `system` is deliberately not used (it depends on each
  viewer's OS, not on the palette).
- Formatting trap found while moving the CSS out: an indented string is
  re-anchored to its minimum content indentation, so inserting `${theme.css}` at
  column 0 re-indented all 500 lines of embedded HTML. Keep interpolations at the
  same indentation as the surrounding string body.
