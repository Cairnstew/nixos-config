# Controls & Hotkeys Review (packwiz)

Review the **default hotkeys/controls for the whole modpack** — every
keybinding (vanilla + mods) players get — and see whether the pack overrides
them. Minecraft stores ALL controls (vanilla and mod keybinds) in
`options.txt` at the **game root** (`.minecraft/options.txt`), as
`key_<id>:<code>` lines. That file — the pack's shipped copy if it has one,
else the one generated by launching the pack — is the ground truth for "what
controls players get."

This is the review half of the config-review pair. For the write side (shipping
your own default controls) load the `mc-mod-controls-set` skill instead.

## Where controls live

- **`options.txt`** — every keybinding, one `key_*` line each, at the game root.
  Not under `config/`; a pack ships its own by placing `options.txt` at the
  **pack root** (packwiz maps pack-root files 1:1 to the game root on install).
- **Vanilla keybinds** (`key.attack`, `key.jump`, …) come from the game itself.
- **Mod keybinds** (`iris.keybind.reload`, `key.ae2.wireless_terminal`, …) are
  registered by mods; their ids and default codes appear in the generated
  `options.txt` once the pack has been launched. The human-readable label +
  owning mod resolve from the pinned jars' lang files.

## Tools

- `packwiz-controls <pack> [options=<path>] [dataDir=<dir>] [mod=<slug>]` —
  **the review primitive.** Reads the effective `options.txt` (pack-shipped →
  instance-generated → explicit `options` path), decodes every `key_*` binding
  to a readable key, resolves ids to labels + owning mods via the pinned jars'
  lang files, splits vanilla vs mod, and reports **conflicts** (the same key
  bound to two actions).
- `packwiz-controls-set <pack> ...` — the write step (ship/override defaults);
  see the `mc-mod-controls-set` skill.
- `mc-run <pack> monitor=boot` — launch once to **generate** the engine+mod
  default `options.txt` if none exists yet (then re-run `packwiz-controls`).
- `packwiz-config-list <pack>` — confirms the pack's shipped `options.txt` is
  indexed + its preserve state (context for whether players get it).

## Reading `packwiz-controls` output

```
## controls for DragonTech  (source: /mnt/media/.../DragonTech/.minecraft/options.txt)
  pack does NOT ship options.txt — players get engine+mod defaults (shown below)
  keybindings: 283 (vanilla 34, mod 249)

## vanilla
  key.attack                 LMB    key.attack
  key.sneak                  LShift key.sneak

## mod
  iris.keybind.reload        R       Reload Shaders [iris]
  key.ae2.wireless_terminal  Unbound Wireless Terminal [ae2]

## conflicts (same key bound twice)
  R -> iris.keybind.reload, key.epicfight.switch_mode, ...
```

- Header `(source: ...)` tells you exactly which file was reviewed: the pack's
  shipped `options.txt`, an instance-generated one, or an explicit path.
- `pack does NOT ship options.txt` → what's shown is the stock engine+mod
  defaults (a fresh player gets exactly this).
- `pack ships options.txt (preserve|overwrite)` → the pack overrides defaults;
  the listing IS the pack's controls. `preserve` = only installed when the
  player has no options.txt yet.
- `mod` section labels resolve from the pinned jar lang files (`[modid]`); an
  unresolvable id just shows the raw id (the mod's lang file may be missing or
  the id doesn't appear in en_us.json).
- `Unbound` = no key assigned (`key.keyboard.unknown`).
- `conflicts` = keys the pack would bind to multiple actions (a real QA signal:
  two mods both defaulting to, e.g., `R` or `LAlt`).

## Workflow: review the default controls for pack P

1. **Pick the source.** Default behavior reads the pack's shipped `options.txt`
   if present, else auto-detects the pack's Prism instance generated file.
   - No instance yet → `mc-run P monitor=boot` once, then re-run.
   - Want a specific file → pass `options=<path>`.
2. **Run `packwiz-controls P`.** This is the complete review: totals, vanilla
   split, mod split with labels/owners, conflicts.
3. **Filter to one mod** with `mod=<slug>` if the request is about a specific
   mod's keys.
4. **Answer the question** with the decoded table. Quote specific bindings as
   `<id> = <decoded key>` (e.g. `iris.keybind.reload = R`), noting the source
   file (shipped vs generated) so it's clear whether that's pack-enforced or a
   mod default.

## Workflow: get one binding's default

- Run `packwiz-controls P mod=<mod>` (or the full listing) and read the line.
- State clearly: is this the **pack-shipped** value (pack overrides) or the
  **mod default** (pack ships no options.txt)? If pack-shipped, note `preserve`
  state — with `preserve`, a player who already ran the pack won't get it.

## Accuracy rules

- **Always review from an actual `options.txt`** — the pack's shipped copy or
  one generated by launching. Never guess a mod's default key from Modrinth or
  a wiki; the code that registers a keybind isn't in any config file, and the
  generated `options.txt` is the only accurate record of it for THIS pack.
- **Don't fabricate.** If `packwiz-controls` errors or shows no `key_*` lines,
  report that and diagnose (missing instance, no options.txt, empty pack) —
  don't improvise bindings.
- The label/owner lookup reads pinned jars' `assets/<modid>/lang/en_us.json`.
  A missing label is normal (some mods don't ship key translation strings) —
  the raw id is still accurate.
- Vanilla ids are exactly the fixed `key.*` set (attack, jump, …); mod ids are
  everything else (either `<modid>.<name>` or `key.<modid>.<name>`).

## Gotchas

- **`options.txt` is a game-root file, not a config file.** It does not belong
  under `config/`. A pack-root `options.txt` maps to the game root; `config/`
  files map to `config/`. Reviewing a pack's controls therefore looks at the
  pack ROOT, not `config/` — `packwiz-config-show` won't find it.
- Mods with zero keybindings simply contribute nothing to `options.txt` —
  that's a valid, complete answer.
- The generated `options.txt` also contains non-key settings (graphics, sound,
  …). `packwiz-controls` ignores those; only `key_*` lines matter for controls.
- Conflicts aren't always a bug — some mods intentionally share a key and rely
  on the player to rebind. Report them, let the user decide.
- A pack that ships `options.txt` with `preserve` never updates existing
  players' controls on reinstall; only fresh installs get the pack's defaults.

## Example

```
user: what are the default hotkeys in DragonTech, and does the pack override any?

1. packwiz-controls DragonTech
   → source: <instance>/.minecraft/options.txt (instance-generated)
     pack does NOT ship options.txt
     283 keybindings (34 vanilla, 249 mod); conflicts listed (e.g. R shared by
     iris.keybind.reload / epicfight.switch_mode / dragonsurvival.next_ability)
2. report: the pack ships no options.txt, so every player gets engine + mod
   defaults; list notable mod keys (iris reload = R, ae2 wireless = Unbound, …)
   and the conflicts the pack should consider rebinding.
```
